# p-x402 test vectors

Language-neutral cases that pin down the p-x402 wire protocol (x402 v2, scheme `exact`, network
`pix:br`, asset `BRL`). They are generated from the TypeScript reference implementation, so an SDK
in another language that passes them speaks the same protocol as `packages/core`,
`packages/client`, `packages/server` and the facilitator.

```bash
bun run vectors          # regenerate the JSON files from the TypeScript code
bun test spec            # check the committed files and replay every vector against the code
```

`vectors.test.ts` fails when a committed file differs from what `generate.ts` produces (someone
changed the protocol without regenerating) and when any vector disagrees with the implementation.
The JSON files are generated: never edit them by hand.

## Files

| File | Cases | What it pins down |
|---|---|---|
| `header-codec.json` | 21 | `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE`: decoded object ↔ exact header string, plus decoder edge cases |
| `validation.json` | 43 | valid and invalid `PaymentRequired`, `PaymentRequirements`, `PaymentPayload`, `SettlementResponse`, with the error code for each invalid one |
| `requirement-matching.json` | 17 | (accepted, required) pairs: match, or the mismatch code and field |
| `client-transcripts.json` | 15 | request/response transcripts a client replays: payment, retries, refusals, spending policy |
| `error-codes.json` | 31 codes | every stable error code, its group and a one-line meaning |
| `paywall-transcripts.json` | 25 | the server SDK core against a scripted facilitator: charge creation, per-IP cap, verify → handler → settle, settle retries, locks, refusals |

Every file is one JSON object:

```json
{
  "$comment": "Generated by ... Do not edit.",
  "formatVersion": 1,
  "area": "header-codec",
  "format": { "...": "rules for this area, in prose" },
  "cases": [{ "id": "payment-required/basic", "description": "...", "...": "inputs", "expected": {} }]
}
```

`id`s are stable: a case keeps its id when its content is regenerated, and a removed id is never
reused. `formatVersion` changes only when the shape of the files changes. All ids, timestamps,
amounts, Pix keys and names are fixed and fictitious (`api.example.com`, `loja-exemplo`, a made-up
random Pix key); nothing is real personal data.

## How to consume them

Load the files with an order-preserving JSON parser (Python's `json` keeps key order). Run one test
per case, named by `id`.

### header-codec.json

The header value is standard base64 (RFC 4648 section 4, alphabet `A-Z a-z 0-9 + /`, padded with
`=`) of the UTF-8 bytes of the compact JSON of the object.

- `direction: "both"`: check `encode(decoded) == encoded` byte for byte, and
  `decode(encoded) == decoded`. `json` is the exact JSON text between the two, and `padding` is how
  many `=` the header ends with (cases cover 0, 1 and 2).
- `direction: "decode"`: decode `encoded` (or `encodedRepeat.char` repeated `encodedRepeat.count`
  times) and compare with `expected`: either `{ok: true, decoded}` or `{ok: false, errorCode}`. The
  only decode error code is `invalid_header`.

Getting the bytes identical takes three things a JSON library may not do by default:

1. **No whitespace**: separators `,` and `:` (Python: `separators=(",", ":")`).
2. **Raw UTF-8, not `\uXXXX`**: `"Relatório"` is written as the bytes `c3 b3`
   (Python: `ensure_ascii=False`). `/` is not escaped.
3. **Key order**: keys in the order of the vector's `decoded` object. The reference decoder returns
   objects in schema order (`x402Version, error, resource, accepts, extensions`;
   `scheme, network, amount, asset, payTo, maxTimeoutSeconds, extra`; `url, description, mimeType`;
   `success, errorReason, payer, transaction, network, amount, extensions`) and drops unknown keys,
   while keys inside `extra`, `payload` and `extensions` keep the order they arrived in. See
   `decode/key-order-and-unknown-keys`. A client that re-encodes a requirements object it received
   (as the retry's `accepted`) should keep it in this order so its `PAYMENT-SIGNATURE` is
   byte-identical to the transcripts. Receivers never depend on key order.

The decoder is lenient in two ways that SDKs should copy: it trims surrounding whitespace and it
accepts missing padding. It refuses the URL-safe alphabet, invalid UTF-8, and anything longer than
`format.maxHeaderLength` (16384) characters after trimming.

### validation.json

Each case has `type`, `value` and `expected`: `{valid: true}` or `{valid: false, errorCode}`. The code
is the one the reference returns where that object is checked (also in `format.types`):

- `PaymentRequired`, `SettlementResponse`: decoding the header on the client. Any failure is
  `invalid_header`.
- `PaymentPayload`: the paywall reading `PAYMENT-SIGNATURE` (HTTP 400, body `{"error": code}`).
  Not a `PaymentPayload` is `invalid_header`; a `PaymentPayload` that is not a p-x402 Pix payload
  (`payload.chargeId` missing, `accepted` not Pix) is `invalid_payload`.
- `PaymentRequirements`: checked against the p-x402 Pix profile by the facilitator's `/verify` and
  `/settle`. Not x402 requirements at all is `invalid_payload`; another scheme or network is
  `unsupported_scheme` / `unsupported_network`; any other Pix profile failure is
  `invalid_payment_requirements`.

An SDK can apply the same split: its generic x402 model, then its Pix model.

### requirement-matching.json

`expected` is the result of `matchPixRequirements(accepted, required)`: `{ok: true}` or
`{ok: false, reason, field}`. `accepted` is what the client put in `PAYMENT-SIGNATURE`, `required`
is what the server requires now. Order of checks (first difference wins): `amount`
(`amount_mismatch`), `payTo` (`pay_to_mismatch`), `scheme`, `network`, `asset`, `maxTimeoutSeconds`
(`requirements_mismatch`), `extra.resourceUrl` (`resource_mismatch`), then every key of
`required.extra` except `chargeId`, `brCode`, `brCodeBase64` and `expiresAt`
(`requirements_mismatch`). A missing `extra.assetTransferMethod` counts as `pix-charge`; keys only in
`accepted.extra` are ignored. Amounts compare as strings.

### client-transcripts.json

Each case configures one client (`client.policy`, `client.retry`, `client.clockStart`, a payer that
pays the BR Code) and makes one or more `calls` in order, sharing its spending total. For each call:

1. Make `request` (method, URL, headers set by the caller, such as a `payment-signature` to resume).
2. Serve `exchanges[i].response` to the client's i-th HTTP request, and assert that the request it
   sent equals `exchanges[i].request` (method, URL and every header; names are lowercase, compare them
   case-insensitively). A response with `redirected: true` and `url` stands for a redirect the HTTP
   library already followed.
3. Compare what the payer was asked to pay (`payments`), how long the client slept (`sleepsMs`; the
   client's clock starts at `clockStart` and moves only by its own sleeps), the result (`outcome`)
   and the spending total after the call (`spentAfter`, centavos).

`outcome` is `{type: "response", status, body}` or `{type: "error", code, reason?}`, where `reason`
is the detail for `policy_exceeded` (`max_per_request`, `max_total`, `origin_not_allowed`,
`redirected`, `resource_origin_mismatch`) and BR Code refusals (`brcode_amount_mismatch`).

The rules the transcripts encode:

- Only a 402 with a `PAYMENT-REQUIRED` header is a challenge; anything else is returned as is.
- Checks happen before paying, in this order: the 402 was not reached through a redirect, a valid
  Pix option exists, its `resourceUrl` equals `resource.url` and has the request's origin, the origin
  is allowed, the BR Code's amount (tag 54) equals `amount`, `amount <= maxPerRequest`,
  `spent + amount <= maxTotal`. The amount counts as spent as soon as the payer is called.
- The retry is the same request plus `PAYMENT-SIGNATURE: base64(JSON{x402Version: 2, resource,
  accepted, payload: {chargeId}})`, where `resource` is the challenge's resource and `accepted` the
  chosen option as decoded.
- On `402` with `PAYMENT-RESPONSE` `errorReason: settlement_pending` the client sleeps
  `max(Retry-After in ms, backoff)` and retries; backoff starts at `initialDelayMs` and is multiplied
  by `factor` after each wait, up to `maxDelayMs`.
- Any other `errorReason` that is a p-x402 code ends the call with that code; an unknown one ends
  it with `payment_rejected`.

### error-codes.json

`codes` lists every stable code with its `group` (`protocol`, `verify-settle`, `infrastructure`,
`webhook`, `client`) and meaning. `client` codes are raised by the client and never sent on the
wire. Codes are never renamed; an SDK should treat an unknown `errorReason` as `payment_rejected`.

### paywall-transcripts.json

For server SDKs. Each case builds one paywall from `config` (facilitator URL, merchant token, a
fixed `clock`, optional `ipRateLimit` and `publicOrigin`) and runs `steps` in order against a
facilitator stub:

- A `request` step hands the paywall `request` (method, URL, headers, `clientIp` for the per-IP
  cap) and `route` (`amount` in centavos, optional `description`, `mimeType`, `resource`).
- `facilitator` lists every request the paywall sends during the step, in order, with the answer to
  serve. Compare method, URL, headers (lowercase names; ignore what your HTTP library adds on its
  own, such as `host` and `content-length`) and the exact JSON body text. The `/settle`
  Idempotency-Key is a random UUID, written as `<uuid>`; it must stay the same across the retries
  of one settle. `{network: true}` stands for a transport error.
- `outcome` is `{type: "response", response}` when the paywall answered by itself, or
  `{type: "paid", chargeId, amount, handler, response?}` when it verified the payment: hand
  `handler` (the route's output) to finalize and compare its result with `response`. `handler:
  "throws"` means the route raised (release without settling); `"hold"` means finalize runs later in
  a `finalize` step, which is how the in-process lock on a charge is tested.
- Responses compare status, every header (lowercase names) and the exact body text.

## Not covered (on purpose)

- **Facilitator HTTP API** (`/pix/charges`, `/verify`, `/settle`, `/supported`, webhooks): SDKs
  talk to the facilitator through the server SDK; vectors for it belong with an OpenAPI export.
- **Server behaviour against a real facilitator**: `paywall-transcripts.json` covers the paywall
  core against a scripted facilitator; the facilitator's own decisions are not vectors.
- **BR Code parsing** beyond the amount check in `client/br-code-amount-mismatch` (CRC, nested EMV
  templates, dynamic codes).
- **Timeouts**: giving up on `settlement_pending` (`payment_timeout`) depends on the charge's
  `expiresAt` or a maximum wait, which is being changed (see below). No transcript waits that long.
- **Concurrency**: two calls racing for the spending total.
- **Payer failures** (`payer_failed`) and redirects of the paid retry.
- **JSON Schema / OpenAPI**: not exported here.
